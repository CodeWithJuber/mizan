# ForgeKit for coding agents

Every coding agent that works on MIZAN runs with [ForgeKit](https://github.com/CodeWithJuber/forgekit) (`@codewithjuber/forgekit` on npm). It adds the same checks to Claude Code, Codex, Gemini CLI, Cursor, Copilot and the other agents: they run as hooks, not as text in a prompt, so they still apply after a context compaction.

## What it does here

| Check | When it runs |
|---|---|
| **dep-gate** | Before an install command or a manifest edit. It blocks a package name that is not on its registry or that OSV lists as malicious. |
| **secret-redact** | After every tool call. It scrubs credential-shaped values from tool output. |
| **protect-paths** | Before an edit. It refuses to write a protected file. |
| **completion gate** | When the session stops. It refuses "done" when code moved without test evidence. |
| **session memory** | At session start and stop. It loads and saves lessons kept in the repository (`forge recall`, `forge remember`). |
| **forge-cortex** | An MCP server (`.mcp.json`) that agents query for impact, recall and the code atlas. |

## Files

The files are generated by `forge init --tools all --no-settings` and `forge hooks on`.

| File | Purpose |
|---|---|
| `AGENTS.md` | The shared rules. ForgeKit owns only the block between `forge:begin` and `forge:end`. `CLAUDE.md` imports it on its first line. Pi and Hermes Agent read `AGENTS.md` directly. |
| `.forge/forge.config.json` | The tool selection (`all`), project hooks, and `verify.exclude` (`packages/bayan` has no runnable suite). |
| `.mcp.json`, `.cursor/mcp.json`, `.vscode/mcp.json`, `.roo/mcp.json`, `.zed/settings.json`, `.gemini/settings.json`, `.kimi-code/mcp.json`, `.openclaw/mcp.json`, `.pi/mcp.json`, `.codex/config.toml`, `opencode.json`, `.continue/` | The `forge-cortex` MCP entry, plus rules for each agent. Pi loads `.pi/mcp.json` after you trust the project. |
| *(none)* | **Hermes Agent** reads `AGENTS.md` and keeps MCP servers per profile, so add forge-cortex once on your machine: `hermes mcp add forge-cortex --command forge --args cortex-mcp`. |
| `.claude/settings.json`, `.codex/hooks.json`, `.gemini/settings.json`, `.cursor/hooks.json`, `.github/hooks/forge.json` | Project hooks (`forge hooks on --hosts claude,codex,gemini,cursor,copilot`). Each one calls `forge hooks run <host> <event>` on the installed CLI, and does nothing when `forge` is not on PATH. |

## What runs when a session starts

No file from the repository is executed by a hook. Each hook line calls the `forge` program installed on the machine, never a script that a branch can change. That is why there is no session-start script here, and no OpenCode plugin: both would be JavaScript or shell taken from whatever branch is checked out, run before any approval prompt. An OpenCode user runs `forge hooks on --hosts opencode` on their own machine.

The hook *lines* themselves still live in the repository, like any project's `.claude/settings.json`. So a pull request that changes an agent's hook or MCP files must be read by eye before anyone opens a checkout of it:

- `scripts/ci/agent-config-guard.sh` runs in CI's first job. It lists every changed file an agent executes or loads (`.claude/settings.json`, `.codex/`, `.gemini/`, `.cursor/`, `.github/hooks/`, `.opencode/`, the MCP files, `.forge/`, `AGENTS.md`, the skills under `.claude/skills/` and `.agents/skills/`, …).
- It fails a pull request that changes any of them unless the repository owner wrote it, or a maintainer has read the change and added the label `agent-config-reviewed`. CI runs again when a label is added.
- Do not open a contributor's branch in a coding agent before that review: check it out with hooks off (`FORGE_HOOKS=0`), or read the diff on GitHub first.

## Memory (Jev)

ForgeKit 1.26 asks Jev, TypeSafe's typed decision model, to decide in each of its five memory layers (`forge memory`):

| Layer | Jev decides | What it may change |
|---|---|---|
| working | which memories enter the context of a task | drops what it judges unneeded |
| episodic | which earlier session is replayed for a new task | picks a better one, or stays silent |
| semantic | whether a fact given to `forge remember` is durable, a duplicate or a contradiction | refuses a one-off (`--force` overrides), skips a duplicate |
| procedural | which repeated, test-confirmed work becomes a skill | writes `.claude/skills/forge-learned-<slug>/` (one a day, eight in all) |
| forgetting | what has gone unused for 30+ days | moves it to the attic, never a decision |

A change to stored memory needs p ≥ 0.8, can be undone (`forge memory skills --remove <slug>`; archived memory goes to the attic, and new evidence restores it), and is journaled in `.forge/jev-memory.jsonl`, which stays local.

**Turning it on.** Jev needs `TYPESAFE_API_KEY` and the decisions opt-in. MIZAN's development sessions use all five layers:

```bash
export FORGE_LLM=1 FORGE_JEV_MEMORY=all   # TYPESAFE_API_KEY comes from the environment
forge memory                              # which layers are on, calls, latency, overrides
forge memory admit "<task>"               # full vs admitted memory tokens for a task
```

ForgeKit never reads the opt-in from the repository: a branch cannot switch paid calls on for a contributor. In cloud sessions the environment's variables set it. Without the key, or on a failed call, every layer behaves as it did before 1.26.

**What carries over.** A cloud session starts from a fresh clone, so memory survives only if it is committed. `.forge/forge.config.json` sets `"portableMemory": true`: facts (`forge remember`) are written as Markdown under `.forge/brain/facts/`, lessons under `.forge/lessons/`, decisions in `.forge/decisions.md`. They are reviewed in the pull request like code, and this repository is public, so they are public. The raw ledger records (`.forge/ledger/*`) stay on the machine; a new checkout rebuilds them from the Markdown. Learned skills appear under `.claude/skills/`, and the agent-config guard asks for a reviewed pull request before they reach `main`.

## Staying on the latest version

The CLI is installed outside the repository, so updating it is the machine's job:

- **Cloud sessions.** The environment's setup script installs it before the session starts. Paste this in the environment's settings (environment menu in the session's title bar → Edit → Setup script); the change can only be approved from a computer, not the mobile app:

  ```bash
  npm i -g @codewithjuber/forgekit@latest
  bash "$(npm root -g)/@codewithjuber/forgekit/install.sh" --no-settings
  ```

  The second command links the skills, crew and rules. `--no-settings` keeps `~/.claude/settings.json` untouched, which matters: a user-level ForgeKit install would switch the project hooks off.
  The environment's variables also set `FORGE_LLM=1` and `FORGE_JEV_MEMORY=all` for Jev (see Memory above); `TYPESAFE_API_KEY` is kept there as well.
- **Your own machine.** `npm i -g @codewithjuber/forgekit@latest` again whenever you like; `forge update --check` tells you when a release is out.
- **Turning it off.** `FORGE_HOOKS=0` turns all the hooks off for one shell.

## Everyday use

```bash
forge doctor           # check the wiring
forge hooks            # which agents have project hooks
forge impact <symbol>  # files an edit will probably touch
forge verify           # pytest at the root and vitest in frontend/, bound to this tree
forge vet <package>    # is this package real and not known malicious?
forge remember <name> "<fact>" && forge sync   # a lesson every agent sees
```

To change the shared rules, edit ForgeKit's `source/` in the ForgeKit repository, or run `forge remember` here, then `forge sync`. Do not edit inside the `forge:begin`/`forge:end` block.

`forge doctor` warns "settings missing" in a cloud session. That warning is expected: the hooks are wired per project, not in `~/.claude`. Do not run `forge doctor --fix` there, because it writes user-level hooks and switches the project hooks off.
